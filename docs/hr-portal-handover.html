1. HR Portal Overview

The HR Portal is the people-management side of the 2B Environmental platform. It has two faces that share one users table and one login system:

SideWho uses itWhat they do
Admin back office (the "HR Portal" cards on the dashboard)Office staff / managers (any non-employee role)Manage employee accounts, documents, announcements, the team calendar, incident reports, quarterly assessments, PTO, and Google reviews.
Employee Portal (public site, employee login)Field crew / employees (role = employee)Log in to see their documents (read & sign), announcements, calendar, reviews, their PTO balance, submit incident reports, manage their profile.

An "employee" is simply a User whose role slug is employee. The same email/password works only on the correct side — the system blocks an employee from the admin login and vice-versa.

New in this release
Three HR modules were added: Quarterly Assessment (§5), PTO tracking (§6), and Company Google Reviews (§11). They are marked NEW throughout.

2. Roles & Permissions

Every admin HR screen is protected by a granular permission (slug = module.action). A role either holds a permission or it doesn't; the superadmin role holds everything. The HR Portal dashboard cards only appear for modules the logged-in user can view.

Roles & permissions themselves are managed under User Management (Roles / Users / Permissions) — outside the HR Portal but controlling access to it.

3. Employee Authentication (Portal Login)

Employees log in on the public site, not the admin panel. Authentication uses Laravel's standard session guard; the role slug keeps the two worlds separate.

Login flow
1. Employee opens the portal and clicks Employee Login → 2. enters email + password → 3. system verifies they hold the employee role and are active (else logged back out with a message) → 4. session starts and a password-hash fingerprint is stored → 5. redirected to their Dashboard.
  • Forced re-login on password change: the EmployeeAuth middleware compares the stored fingerprint to the current password hash on every request — if an admin (or the employee) changes the password elsewhere, other sessions are logged out automatically.
  • Forgot password: a proper tokenised reset — employee requests a link, receives an email, sets a new password. The reset link points to the employee-portal reset page (not the admin one).
  • Key routes: frontend.employee_login, …_authenticate, …_forgot_password, …_send_reset_link, …_reset_password, …_logout.

4. Employees (HR Management & Onboarding)

Where admins create and manage the people who can access the Employee Portal. Each employee is a User with the employee role assigned automatically.

4.1 Admin flow — create & onboard

Onboarding flow
1. Admin → Employees → New Employee → enters name, email, start date, eligibility, and a password → 2. account is created with the employee role → 3. a welcome email with the login credentials is sent automatically → 4. the "welcome sent" date is stamped so it's never sent twice.
  • Mail safety: if the welcome email fails to send, the account is still created and flagged "welcome pending." On the next edit, if a new password is entered, the welcome email is retried (passwords are hashed and can't be re-read, so a fresh password is required to resend credentials).
  • Edit lets admins update name/email/status, set a new password, toggle PTO eligibility, set the start date, record quarterly assessments, and manage PTO (see §5–§6). It also lists the employee's signed documents.
  • Delete is a soft delete (recoverable).
  • List view shows each person's status, quarterly-assessment status, and PTO remaining at a glance.
ActionRoute name
List / Create / Storeadmin.employees.index / create / store
Edit / Update / Deleteadmin.employees.edit / update / destroy
Record assessment / PTO entryadmin.employees.complete-assessment, admin.employees.pto.store

5. Quarterly Assessment NEW

Tracks when each employee is due for their 90-day review and reminds admins automatically.

5.1 How it works

  • The admin sets the employee's Start Date (hire date).
  • The system counts 90 days from the start date (or from the last completed assessment) to compute the next-due date.
  • It recurs: every completed assessment schedules the next one 90 days later.
Assessment flow
1. Admin sets Start Date → 2. at 90 days the employee becomes Due → 3. a daily job notifies all admins (dashboard bell + email) → 4. admin opens the employee, clicks Mark Completed (optional notes) → 5. it's logged in the history and the next due date resets to +90 days.
  • Where to see it: a "Due / On track / Completed" status column on the Employees list, and a full status + history card on each employee's edit page.
  • Reminders: the assessments:check-due command runs daily (9 AM Honolulu); it notifies once per cycle (no daily spam) and re-arms when an assessment is completed. Admins get both a dashboard bell notification and an email (branded template).

6. Paid Time Off — PTO NEW

A simple, admin-maintained PTO tracker in days. The app shows each employee their allotment, days used (with dates), and remaining — counting down from the full year's amount so balances never look alarmingly negative.

Important — source of truth
Payroll remains the official record and still calculates accrual. This module is a clear visibility tool for the crew; it does not calculate accrual, run payroll, or compute termination payouts.

6.1 How it works

PTO flow
1. Admin marks the employee PTO-eligible → 2. adds an Annual allotment entry (e.g. 27 / 16 / 11 days) at the start of the year → 3. as the employee takes time off, admin logs a PTO used entry (date + days, half-days allowed) → 4. the app shows Allotted / Used / Remaining → 5. at year-end, up to 5 days can be carried over (entered as a "Carried over" entry in the new year).
Entry typeEffectExample
Annual allotmentadds the year's days (+)+27 days on Jan 1
Carried overadds prior-year days, max 5 (+)+3 days carried from last year
PTO usedsubtracts a day/part-day, dated (−)−1 day (vacation), −0.5 (half day)
Adjustmentmanual correction (+/−)±X with a note
  • Admin view: on the employee edit page — an Allotted / Used / Remaining summary, an "Add PTO entry" form, and a full dated history. The Employees list also shows each person's remaining days.
  • Employee view: a "My Paid Time Off" card on their dashboard showing remaining / allotted / used plus the dates they've taken — read-only, with a note that the paystub is the official record. If nothing is set yet, it shows a friendly "not assigned yet" / "not enrolled" status.
  • Everything is admin-entered (no employee request workflow in this version); the balance is the signed sum of all entries, so every change is auditable.

7. Document Management & E-Signature

Admins upload documents into folders and either publish them company-wide or assign them to specific employees. Some documents require a mandatory "read & sign," which produces a signed certificate.

7.1 Admin flow

  • Create folders (categories), then upload documents into them.
  • A document is either public (everyone) or personal (assigned to chosen employees).
  • A personal PDF can be marked "requires acknowledgment" with a due date — the employee must read & sign it.
  • Compliance screens: a Sign-offs dashboard (who still needs to sign) and a per-document Acknowledgments view (signed vs pending), with downloadable certificates.

7.2 Employee read-and-sign flow

Read & sign flow
1. Employee sees the document under "Action Required" → 2. opens the read & sign screen → 3. types their name & ticks agree → 4. the system generates a Certificate of Acknowledgment PDF (name, IP, timestamp), records the signature, notifies admins, and unlocks the original file for download.
How "signing" works
The typed name is the signature. The system renders a separate certificate PDF (preferring headless Chrome for crisp output, falling back to the built-in PDF engine). The original file stays locked until the employee has signed. Read-and-sign is limited to personal PDF documents.

8. Announcements

  • Admins post company news with an optional image and publish date. Each announcement has a unique URL slug.
  • Employee side: announcements are viewable by everyone (even logged-out) on the portal; the 3 latest also appear on the employee dashboard.
  • Routes: admin admin.announcements.*; public frontend.employee_announcements / …_announcement.

9. Community Calendar

  • Admins add events (title, dates, all-day or timed, category, location, optional flyer attachment). Categories are colour-coded (Holiday, Meeting, Training, PTO, Other).
  • The calendar is rendered by FullCalendar, fed by a JSON events endpoint; all-day vs timed events are handled correctly, with soft category colours.
  • Employee side: a read-only calendar of upcoming events on the portal.
  • Routes: admin admin.community-calendar.* (incl. …events); public frontend.employee_calendar / …_events.

10. Incident Reports

Workplace-incident reporting, filed by employees from the portal or by managers on their behalf.

10.1 Flows

Employee-filed
1. Employee → Report an Incident → fills date, time, location, category, description, and attaches up to 6 photos + 4 videos → 2. gets a reference number (IR-YEAR-####) and a thank-you page → 3. all admins are notified.
Admin review
1. Admin opens the report → 2. reviews details/media → 3. changes status (Open → Under Review → Closed), adds review notes → 4. the reporter/involved employee is notified of the status change.
  • Permissions & scope: managers (holders of incident-reports.edit) see and manage all reports; a regular employee sees only their own.
  • Extras: list filters + year dropdown, CSV export, per-photo delete. Media (photos and videos) are stored together and kept on disk even if a report is soft-deleted.

11. Company Google Reviews NEW

Shows the company's Google Business Profile reviews inside the Employee Portal so the crew can see what customers are saying.

Data flow
1. A daily job pulls reviews from Google → 2. stores them locally → 3. the portal's Reviews page shows the overall rating, each review (name, stars, date, comment), and any owner replies.
Status — go-live pending
The page and the whole sync pipeline are built and currently show sample reviews. Going live needs the client to grant Google Business Profile access and Google to approve API access; then 5 credentials are added to the config and the daily sync replaces the samples with real reviews — no code change required.

Routes: employee page frontend.employee_reviews (/company-reviews). Commands: reviews:sync (daily), reviews:seed-sample (loads previews).

13. Activity Log (Audit Trail)

  • Create / update / delete / restore actions on key HR records (employees, documents, announcements, incident reports, calendar events, roles, permissions) are recorded automatically with the acting user, time, and what changed.
  • Login / logout and document-signing events are also logged.
  • The admin Activity Log is split into HR and Forms views, each with module/user/date filters.
  • Note: operations run from the command line (migrations, scheduled jobs) are intentionally not logged.

16. Deployment Notes

  1. Database: the new HR tables/columns (quarterly assessments, PTO, Google reviews, plus the new users columns) must be applied. On this project a plain artisan migrate is out of sync, so apply them via migrate --path=… per migration or the supplied raw SQL.
  2. Server cron must run schedule:run every minute for the assessment/review jobs.
  3. Google Reviews: fill the 5 credential values once the client grants access & Google approves; until then the portal shows sample reviews (load with reviews:seed-sample).
  4. PTO: create the crew's employee accounts, then enter each one's annual allotment to start tracking.
  5. Mail: SMTP must be configured for welcome emails, document/assessment notifications, and password resets.

End of HR Portal handover. This document describes behaviour and flows; exact field-level logic lives in the respective controllers, models, and Blade views (Employees, Documents, Announcements, Incident Reports, Calendar, plus the new Quarterly-Assessment, PTO, and Google-Reviews code).
